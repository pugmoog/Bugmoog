Bugmoog

Progress saving

The unified save system stores its durable records in bugmoog-saves-v1, an IndexedDB database belonging to the website where the menu is running. Websites naturally have separate saves through browser origin isolation. Bugmoog still runs as a bookmarklet; no new domain, account, synchronization server, or game URL changes are required.

Implemented

  • Early restore: each local game HTML document loads the save runtime before its game scripts. The wrapper receives the current website’s record before navigating to the game.
  • Storage coverage: per-game localStorage, cookie values with path/expiry handling, and IndexedDB schemas and records. The archive preserves binary buffers, typed arrays, blobs, dates, maps, sets, and cyclic structured data.
  • Database-backed games: game databases use an isolated temporary namespace on the asset host while running, then their snapshots are persisted on the launching website. The namespace is random per launch, restored exclusively from that website’s record, and never used as a shared profile. Temporary databases are deleted on normal close; previously recorded temporary databases are cleaned up on the next launch.
  • Workers and filesystems: classic and module workers use the same temporary database namespace. Emerald’s emulator save function and filesystem are flushed before export and close; exposed Emscripten/Unity filesystems are flushed as well. Emulator ROM/core cache databases are excluded.
  • Automatic saving: storage changes are debounced; committed database writes trigger snapshots. Periodic and visibility-change flushing reduces dependence on tab unloading. Back waits for save acknowledgement before clearing the game.
  • One portable archive: the Saves menu downloads a versioned JSON file or copies an equivalent text code. It includes captured records for closed games as well as the currently running game. It never exports unrelated website storage or cookies.
  • Import and undo: file/code imports are validated and previewed with per-game replace/skip choices. Existing saves are kept as a rollback copy, and importing updates the selected records atomically. Importing on another website explicitly copies progress there, without changing the source website.
  • Conflicts and failures: a lease prevents two tabs from saving the same game concurrently; revision checks reject stale writes. Export/import requires other active game tabs to close. Failed writes are visible and the running game offers a recovery download. It is not closed while an unacknowledged save is failing.
  • Legacy records: opening a game offers to copy its old __fakeLocalStorage__:/__fakeCookies__: buckets if found and the new website has no save. The old records are retained. Native legacy databases and unnamespaced localStorage are not swept or silently attributed to a website.

Limits

  • External frames, server-side account progress, and game-specific in-memory state without a save API cannot be captured automatically. Detected unsupported frames/storage methods are listed with that game and require acknowledgement when exporting.
  • A game must actually save its progress. Export does not turn a game without persistence into a saveable game or create a universal emulator save state.
  • Some engines keep files in a private closure; they need a specific flush hook if their normal save process does not write IndexedDB promptly. Only exposed engine filesystems can be flushed generically.
  • Shared workers, service-worker persistence, and private filesystem storage need dedicated adapters. Third-party storage restrictions can prevent the temporary game databases from opening even when host storage is available.
  • Database snapshots currently copy complete changed databases. Large worlds take more time and space to snapshot/export. Files are preferable to copyable codes for large saves; the import limit is 512 MB.
  • A browser crash or forced tab termination can lose changes that have not reached the launching website. Clearing that website’s browser data removes its saves; a downloaded backup is the recovery method.
  • Only the current website’s saves are exported. Other websites’ storage is not read or combined.
  • This is a local repository implementation, not a published deployment. Passing storage integration checks is not a promise that every game’s gameplay and save behavior has been verified.

Files

save-host.js owns host persistence and UI; save-wrapper.js coordinates games; save-runtime.js installs the early hooks; save-idb.js handles native database isolation/snapshots; save-common.js validates and encodes archives.
